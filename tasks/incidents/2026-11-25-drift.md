## What the diff contains

All 12 statements are **default privileges** for objects that role `postgres` will create in schema
`public` in the future. There are no tables, columns, functions, policies or data in the diff, and the
production migration history is empty (read-only check). The diff has no secrets, so it is quoted here:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON SEQUENCES FROM "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON SEQUENCES FROM "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON SEQUENCES FROM "service_role";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON FUNCTIONS FROM "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON FUNCTIONS FROM "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON FUNCTIONS FROM "service_role";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON TABLES FROM "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON TABLES FROM "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" REVOKE ALL ON TABLES FROM "service_role";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT MAINTAIN, REFERENCES, TRIGGER, TRUNCATE ON TABLES TO "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT MAINTAIN, REFERENCES, TRIGGER, TRUNCATE ON TABLES TO "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT MAINTAIN, REFERENCES, TRIGGER, TRUNCATE ON TABLES TO "service_role";
```

`supabase db diff` prints the SQL that would turn the database built from `supabase/migrations` into the
target (production). So, read together:

- **Database built from our migrations (local CLI 3.2.0 image):** the Supabase default. Future tables,
  sequences and functions in `public` are granted ALL to `anon`, `authenticated` and `service_role`.
- **Production:** future sequences and functions get no grants for those roles. Future tables get only
  `MAINTAIN, REFERENCES, TRIGGER, TRUNCATE`, so **no `SELECT`, `INSERT`, `UPDATE` or `DELETE`**.

## Cause

Production's default privileges in `public` are stricter than the Supabase default the local image uses.
Nobody changed them through a migration (the history is empty) and no agent wrote to production. The most
likely source is the project-creation setting for the Data API (not exposing new tables automatically),
which newer Supabase projects apply when they are created. **Unconfirmed:** the person should check whether
that option was chosen when creating the project, or whether someone ran SQL in the dashboard. If it was
done by hand, this is a rule 4 incident (production changed by hand) as well.

Either way the drift is **real**, not noise. It changes behavior: a table created by a migration would be
usable by `anon`/`authenticated` locally and in CI (default ALL), but in production the API would return
permission errors until the migration grants privileges explicitly. Tests would pass and production
would fail. So excluding these statements from the drift check is the wrong fix.

## Proposed fix (the person decides; nothing has been changed)

1. **Baseline migration (db-builder, normal PR):** `supabase migration new baseline_default_privileges`
   containing exactly the 12 statements above, so a database built from the repo matches production.
   These statements are idempotent, so when the Supabase integration applies the migration to production
   nothing changes there; no "mark as applied" by hand is needed. After it deploys, the drift check
   should be empty. The migration has no `DROP`/`RENAME`/`TRUNCATE`/`DELETE`, so it isn't destructive
   under verify.sh. It's a DB change, so it waits for stop rule 1 to be lifted for this fix only (the
   person's call), plus the usual gates.
2. **Convention (db-architect, before the first real table):** every migration that creates a table,
   sequence or function in `public` must GRANT exactly what the API needs (for example
   `grant select, insert, update, delete on public.todos to authenticated;`) in addition to RLS and
   policies. Add a pgTAP test that checks the grants, so local and production can't drift apart silently.
3. **Security question (security, then the person):** production's remaining defaults still give
   `anon` and `authenticated` `TRUNCATE`, `TRIGGER`, `REFERENCES` and `MAINTAIN` on future tables. `TRUNCATE`
   is not limited by RLS. Proposal: a separate migration revoking those four from `anon` and
   `authenticated` for future tables in `public` (and checking the existing state). This changes
   production behavior, so it needs security's threat model and the person's approval. It isn't part of
   the baseline.
4. **Integration check (the person):** production migration history is still empty, so the Supabase
   GitHub integration hasn't applied migration `20261125104017_init.sql`. Check its settings (production
   branch `main`, directory `.` (the folder that contains `supabase/`), "Deploy to production" on). The baseline migration in step 1 would
   be the first one it deploys; confirm afterwards with the read-only migration list and a green drift run.
